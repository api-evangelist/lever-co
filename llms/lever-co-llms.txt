# Lever

> Lever is an applicant tracking system (ATS) and candidate relationship management (CRM) platform for
> recruiting teams, owned by Employ Inc. Its public API surface is the authenticated Lever Data API
> (REST, https://api.lever.co/v1) plus an unauthenticated public Postings API (https://api.lever.co/v0/postings)
> used to syndicate job listings to careers sites and job boards.

## What an agent needs to know first

- **Two credential models.** HTTP Basic with an API key (key as username, EMPTY password) is for a customer's own internal workflows. OAuth 2.0 authorization code is the ONLY path for a third-party integration, and the app must be approved through the partner program first. Lever will not issue API keys for integration development.
- **The `audience` parameter is required** on `https://auth.lever.co/authorize` — `audience=https://api.lever.co/v1/` with the trailing slash. Omit it and the consent screen silently grants only `offline_access`.
- **A person and a candidacy are different objects.** A Contact is the human; an Opportunity is one journey through the pipeline for one posting. One Contact has many Opportunities. The `candidateId` still present on webhook payloads is an Opportunity id, not a Contact id.
- **There is no idempotency key.** Retrying a POST creates a duplicate. Read back before retrying a write.
- **`?include=` is subtractive.** By default all fields return; the moment you name one, ONLY that field returns.
- **Ids are bare UUIDs with no type prefix.** An id alone never tells you what kind of object it points at.
- **Timestamps are epoch milliseconds**, not seconds and not ISO 8601.

- [Notes API](https://api.lever.co/v1/opportunities): `listNotes`, `createNote`.
- [Files API](https://api.lever.co/v1/files): `listFiles`, `uploadFile`, `getFile`, `deleteFile`.
- [Requisitions API](https://api.lever.co/v1/requisitions): `listRequisitions`, `createRequisition`, `updateRequisition`, `deleteRequisition`. Requires the TRM Enterprise package or Advanced HR feature.
- [Users API](https://api.lever.co/v1/users): `listUsers`, `getUser`, `createUser`, `updateUser`.
- [Stages API](https://api.lever.co/v1/stages): `listStages`, `getStage`.
- [Archive Reasons API](https://api.lever.co/v1/archive_reasons): `listArchiveReasons`, `getArchiveReason`.

## Limits and runtime behaviour

- Rate limit: token bucket per API key, 10 requests/second steady state, bursts to 20 requests/second. No per-endpoint limits.
- On exhaustion: HTTP 429. **No `Retry-After` and no `X-RateLimit-*`/`RateLimit-*` headers are returned** — schedule your own exponential backoff.
- Pagination: `limit` (1-100, default 100) plus an opaque `offset` token. Response envelope is `{data, next, hasNext}`. Only pass back an offset Lever returned.
- OAuth access tokens expire in 3600 seconds; request `offline_access` for a refresh token.
- Errors: `{"code": "...", "message": "..."}` as `application/json`. Not RFC 9457.

## Reversibility — read before writing

- Archiving an Opportunity is reversible: `updateOpportunity` with the archive reason set to `null` un-archives it. No time window applies.
- Deactivating a user is reversible via the reactivate endpoint.
- **Everything else that removes data is final.** There is no restore for deleted interviews, panels, notes, files, requisitions or webhooks, and no grace period.
- **`PUT /requisitions/{id}` and requisition-field updates delete by omission.** Lever's docs state the removed data "cannot be recovered from within Lever or via our API". Always GET, merge, then PUT.
- The deleted-record endpoints (`/applications/deleted`, `/postings/deleted`, `/opportunities/deleted`) report WHAT was deleted within a 30-day query window. They do not restore anything.
